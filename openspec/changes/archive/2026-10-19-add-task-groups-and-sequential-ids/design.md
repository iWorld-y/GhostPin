# Design

## Context

动机见 `proposal.md` 的 Why。当前实现中与本变更直接相关的事实如下。

- `TodoItem.id` 是 UUID，`TodoItemPayload` 单独维护 CLI 输出字段，CLI 的 `resolveID` 只接受 UUID。通知标识也调用 `uuidString`，App 的点击冷却记录使用 `TodoItem.ID`。
- `TodoStore` 将 `[TodoItem]` 作为整份 JSON 读取和保存。原子文件替换可以避免半写入内容，但没有进程间锁；App 的状态推进和提醒回写可能基于比 CLI 更旧的内存快照。
- `StorageLocations` 已支持显式传入 `applicationSupportRoot`，默认入口会把 TodoPin 旧文件复制到 GhostPin 目录。旧格式的解析校验直接依赖当前 `TodoItem`，更换 ID 类型时必须同时调整迁移链路。
- HUD 的投影已集中在 Core，分组不参与现有投影。另一个活动变更 `hud-doing-focus-and-hover-ghost` 已实现部分 macOS 行为，本变更不调整其分区、聚焦或隐身规则。
- macOS 卡片的优先级标记目前紧跟标题，没有独立的右对齐标记区域；Windows 卡片则把优先级放在详情文本行。两端都需要为本次优先级与组别标记预留标题行右侧空间。
- Windows 的 `Todo`、JSON 编解码和 `TaskRepository` 独立实现了旧 UUID 数组格式。状态推进虽会重新读取文件，但读改写之间没有进程间锁，也没有保存文档级编号信息。
- `GhostPinCoreChecks` 已用显式临时文件 URL 检查 Core。CLI 没有测试数据目录入口，`make verify` 当前会启动默认数据目录下的开发版 App，因此新格式启用前需要补齐验证隔离。

## Goals / Non-Goals

**Goals:**

- 将分组、整数 ID 和编号计数器作为一个存储升级交付，任意写入口都保留完整文档状态。
- 将参数错误、业务目标校验和迁移提交分开，失败命令不能顺带迁移数据。
- 继续使用本地 JSON 和系统文件锁，不新增第三方依赖，存储逻辑留在 Core 或对应的 Windows 存储模块。
- 用隔离文件覆盖真实 CLI 命令、跨进程竞争和迁移失败，验证不依赖真实待办内容。
- 标记布局按实际文本宽度限制组名展示，长标题与长组名不能把标记挤出卡片或改变完整组名。

**Non-Goals:**

- 不提供多标签、多级分组、分组元数据、空组管理或批量改组名命令。组名直接保存在任务上，内置 `默认` 始终可用。
- 不增加分组筛选或编辑 UI、全局快捷键、云同步或跨任务库合并。不同本地任务库可分别从 `10000` 编号。
- 不保留 UUID 操作别名，不支持旧程序继续写新格式。除本次卡片标记外，不同步已有的 macOS 与 Windows HUD 视觉或聚焦差异。

## Decisions

### 1. 使用必填组名，迁移默认值仅作用于旧数据

任务的 `group` 为非空字符串。所有新增入口均要求调用方显式提供组别，Core 不能以默认参数隐藏这个要求。输入去掉首尾空白，随后精确、区分大小写地匹配；组名首次用于任务时即可生效。

`默认` 是内置组名，不需要独立持久化一条分组记录。普通新增指定 `默认` 与指定其他组走同一条校验路径。只有旧 UUID 数组的转换器可以自动补 `默认`，新格式缺组字段属于无效数据。

替代方案是独立分组对象和 `groupID`。当前只需要 Agent 归类与查询，额外分组表会引入创建、删除和空组生命周期，因此本次不采用。

### 2. 整数 ID 由存储分配，所有分组共用序列

Swift 与 Rust 使用一致的整数范围，CLI 的 JSON 输出为整数。为保证 Windows JSON 数字精确往返，任务 ID 最大为 `9007199254740990`，下一编号最多为 `9007199254740991`，用尽时拒绝新增。编号只在成功新增事务中分配，下一编号从 `10000` 开始；换组、完成、重开、删除和普通查询都不推进计数器。

迁移时先按 `createdAt` 升序、再按规范化为小写的 UUID 字符串字典序排序，为全部状态的旧任务依次分配 ID。排序只用于确定映射，任务展示仍按原有业务排序。迁移后的 ID 不再重新计算。

不使用"现存最大 ID 加一"，因为删除最大 ID 或清空任务后会复用编号。也不维护"短号加 UUID"两套运行时标识，旧 UUID 只存在于原始备份中，可按稳定映射规则对照历史引用。

### 3. 计数器与任务保存到同一版本化文档

任务文件保留原路径，顶层由数组升级为对象。

```json
{
  "schemaVersion": 2,
  "nextID": 10001,
  "items": [
    {
      "id": 10000,
      "group": "默认",
      "title": "整理周报",
      "createdAt": "2026-10-19T09:00:00+08:00",
      "status": "todo",
      "priority": "medium"
    }
  ]
}
```

新增文档模型和独立的旧任务解码类型，避免把 UUID 或缺失组别继续混入新 `TodoItem`。旧解码器保留当前缺失 `status`、`priority` 等字段的兼容语义。新文档校验版本、ID 唯一性、组别及 `nextID` 大于所有现存 ID 的条件，计数器无效时拒绝读写，不能从剩余任务猜测历史高位编号。

CLI 的 `list --json` 继续返回任务数组，不暴露存储封装；`TodoItemPayload` 明确输出整数 `id` 和字符串 `group`，其余字段保持现有输出语义。存储数组中可继续省略为空的可选业务字段。

单独保存计数器会造成计数器与任务文件只能分别提交，因此不采用额外计数器文件或 UserDefaults。

### 4. 在固定锁文件上串行执行完整读改写

同一个任务目录使用固定的 `.todos.lock`，锁对象不随 `todos.json` 的原子替换而变化。macOS 使用 `flock`，Windows 使用 Rust 标准库文件锁（Rust 1.89 起可用），不引入新包。

存储入口在锁内重新选择数据源、读取并校验最新文档，再定位目标任务和合并调用方明确请求的字段。新增、换组、状态推进、删除、提醒回写和迁移共用该边界；禁止把锁外快照或锁外合并好的完整任务写回。Core 现有可绕过事务的直接 `save()` 路径需要收敛，检查用例改用明确的夹具写入或事务入口。

原子提交成功后再更新已发布的任务快照。状态推进、提醒回写找不到目标时不能用旧任务重建记录；操作完成后释放锁，进程异常退出时由操作系统释放锁。普通读取也通过统一存储入口，旧数据读取需要升级时在同一锁内处理。

只给新增或计数器加锁无法阻止 App 把新计数器覆盖回旧值，因此锁必须覆盖所有写入口。

### 5. 先验证操作，再一次提交迁移

CLI 先处理帮助，再校验参数及必填组别，随后才进入存储。锁内识别旧数组时，先在内存生成候选 ID 和 `默认` 归属；修改命令先根据候选映射检查目标是否存在，失败时直接返回，不创建迁移备份或新任务文件。

成功查询旧数据或 App 成功加载旧数据时，可以提交一次迁移。成功写命令可以将格式转换与业务修改合并为一次新文档提交，原始备份仍记录业务修改之前的原始内容。迁移两条旧任务后新增一条任务时，新任务使用 `10002`。

原始备份固定为任务目录中的 `todos.v1.backup.json`，写入时必须采用不覆盖已有文件的方式。相同内容的现存备份可复用；不同内容报错，不能覆盖。备份成功后再原子替换目标文件，提交失败保留原任务文件，重复执行按相同规则产生同一映射。

数据源优先级保持 GhostPin 高于 TodoPin。需要从 TodoPin 升级时，在 GhostPin 目录锁内读取源文件，验证成功后直接提交新文档并保留原始备份；TodoPin 源文件不改动。避免旧路径解析在业务校验之前先复制文件，导致失败命令产生迁移副作用。

未知版本、重复 ID、空组或无效计数器都停止读写，不降级为旧数组，也不以空任务覆盖。新格式加载与相同内容比较继续使用规范化编码，防止文件监听导致无意义的重复发布。

### 6. CLI 只新增组别参数，App 适配标识与写入路径

新增要求 `add <title> --group <组名>`。`list` 和 `update` 增加 `--group`，前者可与 `--all`、`--json` 组合，后者只改变目标任务的组别。保留既有字段参数，不提供 `--ungrouped` 或 `--clear-group`。

全部任务 ID 参数改为十进制整数，旧 UUID 输入返回明确错误。命令成功与失败 JSON 保持现有外层结构，删除结果的 `id` 也改为整数。日期、优先级等校验继续保留，并在访问存储前完成与任务内容无关的校验。

App 继续从统一集合生成 HUD 投影。点击冷却使用新的 `TodoItem.ID`，通知标识使用整数的字符串表示；状态与提醒写入经由统一事务保留分组、计数器和外部新增任务。卡片标题行按决策 9 调整标记，不增加窗口、分组筛选或编辑入口。

### 7. Windows 同步存储格式与卡片标记

Windows 的任务模型改为整数标识并保留 `group`，编解码层处理完整文档。`TaskRepository` 保存文档级元数据，状态更新在固定锁文件保护下重新读取、修改并提交，不用 `Vec<Todo>` 重建缺少 `nextID` 的顶层文档。

旧 Windows UUID 数组使用与 Swift 相同的编号排序、默认组、备份和版本校验规则。保留现有 ISO 8601 转换和暂时无效文件的最后有效快照。跨语言夹具在现有 `windows-native/tests/fixtures/` 下增加新格式样例，旧格式样例继续用于迁移检查。

Windows 的 `draw_card` 同步标题行右侧的优先级与组别标记，优先级不再混入详情文本行，避免重复展示。标记位置、宽度和省略规则遵循决策 9；其余既有投影、窗口和显示规则保持原样，不增加 Windows 任务新增 CLI。

### 8. 自动检查使用隔离目录

复用 `StorageLocations` 已有的 `applicationSupportRoot` 注入能力。在开发构建中提供验证专用的 `GHOSTPIN_TEST_SUPPORT_ROOT` 环境入口，使 CLI 子进程和验证启动的 App 都使用临时根目录；该入口不能进入 Release 构建，也不成为安装用户的 CLI 参数或操作契约，不改写 `HOME`。

`GhostPinCoreChecks` 继续手动注册检查，增加以显式临时路径运行的内部子进程模式，用于同时分配编号和模拟 App 旧快照写回。真实 CLI 检查使用开发版进程和验证目录，覆盖参数、退出码、JSON、换组和编号；安装用户的 Skill 仍只使用固定正式入口。

`make verify` 的现有验证模式在启动进程前创建临时根目录并通过验证入口传入，结束后停止验证进程并清理临时夹具。普通开发启动和正式安装入口继续使用原有数据路径。实现和自动验证不能借此直接迁移真实任务。

### 9. 优先级与组别标记在标题行整体右对齐

卡片标题保持左对齐，右侧标记区域依次放优先级和组别。标记区域的右边缘固定在卡片右侧内容边界，标题使用剩余空间，不能让短标题把标记拉向左侧，也不能让长标题与标记重叠。标题多行时，两个标记仍位于标题首行右侧。

组别标记复用现有小号标记的字体、圆角和内边距，优先级保留原有视觉语义。组名文本单行显示，最大宽度按同字体三个汉字的实际宽度约束，外侧内边距单独计算。超出部分使用系统文本的尾部省略，省略号占用上限内的空间，不通过截断存储字符串实现显示限制。

三字符约束只限制可见文本区域，不限制完整组名长度。`默认` 也展示组别标记，长组名在任务数据与 CLI 中保持完整；不增加悬停弹层、额外字段或组名编辑入口。标记作为一组右对齐，不要求优先级和组别分别建立固定宽度列。

macOS 调整 `DesktopNoteCardView` 的标题行布局，Windows 在卡片绘制时为标记测量并预留相同语义的右侧区域。标记不扩大状态按钮的命中区域，不参与分组筛选或换组。视觉验证覆盖最小与正常窗口宽度、短标题、多行标题、默认组、三个汉字组名和超长中英文组名，不引入新的快照测试框架。

## Risks / Trade-offs

- [旧程序不识别新文档] → App 与随包 CLI 一起升级，升级前退出旧进程；Windows 同步兼容，旧 UUID 不保留操作别名。
- [只有新增加锁，状态或提醒仍覆盖新任务] → 将全部写入口纳入锁内重新读取与原子提交，并通过跨进程及旧快照场景验证。
- [失败命令先迁移了真实数据] → 将旧数据转换留在内存，操作验证成功后才备份和提交，并用原始字节对照检查失败命令无副作用。
- [分组按名称保存，整体改名需逐项更新] → 当前采用精确组名和逐任务换组，不引入未要求的分组管理生命周期。
- [旧备份不包含升级后新增或修改] → 回退前另存当前新格式文件，回退仅恢复迁移时快照，不静默丢弃升级后的数据。

## Migration Plan

1. 实施和自动验证先使用临时目录，构造包含 Todo、Doing、Done、相同创建时间及缺省旧字段的夹具。核对全部业务字段、稳定 ID 映射和下一编号。
2. 在准备实际升级时退出旧 App 和旧 CLI 进程，使用同一版本的 App 与随包 CLI。真实任务迁移通过用户实际使用新版本触发，不作为开发验证动作。
3. 首次成功访问在锁内完成原始备份、统一归组、整数编号和新文档提交。新旧目录同时存在时始终以 GhostPin 文件为准。
4. 使用新版本 CLI 回读全部任务，核对任务总数、全部组别、ID 唯一性和字段保留；重复加载和后续显式组别新增应继续使用已保存的下一编号。
5. 回退时先退出新进程并另存当前新格式文件，再按需恢复 `todos.v1.backup.json` 和匹配的旧程序。旧备份只代表迁移时快照；恢复前必须先处理升级后新增和修改的数据，不提供自动降级。
