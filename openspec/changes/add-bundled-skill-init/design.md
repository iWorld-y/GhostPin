# Design

## Context

变更动机见 `proposal.md` 的 Why。当前实现有以下相关约束：

- `script/build_and_run.sh` 与 `script/package_dmg.sh` 分别组装开发 App 和发布 App，均将 CLI 放在 `Contents/MacOS/`，并在复制资源后执行签名。当前两个脚本均未复制根目录的 `skills/ghostpin-cli/`。
- `Sources/GhostPinCLI/main.swift` 使用命令分发和独立的命令处理函数。只有任务命令才创建 `TodoStore`，因此 `init` 可以完全独立于任务存储。成功及失败响应由 `CLIOutput.swift` 编码。
- skill 当前包含 `SKILL.md` 和 `agents/openai.yaml`。已经核实本机安装目录通过符号链接指向项目 skill，因此链接保留和最终目录检查是本次必须支持的行为。
- Core 行为检查集中在 `Tests/GhostPinCoreChecks/main.swift` 并手动注册。`script/check_cli.py` 目前只隔离任务目录，不能直接用现有隔离变量运行会写入真实 skill 目录的初始化命令。

## Goals / Non-Goals

**Goals:**

- 让 App、CLI 和 skill 来自同一份构建输入，初始化只依赖随包资源。
- 将链接解析、归属检查和目录替换集中到可注入路径的独立模块，便于使用临时目录验证。
- 将新副本准备和旧目录替换分开，确保失败结果如实反映实际安装状态，并提供恢复入口。

**Non-Goals:**

- 不增加网络下载、版本比较、自动后台更新或 App 启动时安装。
- 不增加公开的目标目录参数、其他 Agent 安装目录或绕过归属标记的强制选项。
- 不修改任务数据、存储格式、任务迁移、App 写入口或 Windows 的实现与发布行为。

## Decisions

### 1. 将仓库 Skill 目录作为唯一打包来源

两个 App 组装脚本在签名前将整个 `skills/ghostpin-cli/` 复制到 `Contents/Resources/skills/ghostpin-cli/`。根目录新增一个名为 `ghostpin-cli` 的空普通文件，`agents/openai.yaml` 和未来辅助文件随整个目录一起复制。

CLI 根据自身实际可执行文件的位置定位相邻的 `Contents/Resources/skills/ghostpin-cli/`。不根据当前工作目录定位来源，也不将 `/Applications` 中另一个 App、仓库文件或网络资源作为回退来源。开发 App 和临时检查 App 只要具有相同的 Bundle 目录结构，即可使用相同行为。

在修改目标前，校验来源目录及归属标记、`SKILL.md`、`agents/openai.yaml` 的存在和类型。打包检查要求标记为空普通文件；已有目标的归属判定只要求同名普通文件存在，不依赖文件内容。

考虑过单独维护 CLI 资源副本或把 skill 文本嵌入二进制。两种方式都增加了内容同步点，也不便于携带辅助文件，因此采用完整目录复制。

### 2. 先确定真实目标，再检查覆盖归属

逻辑安装位置固定为当前用户的 `~/.agents/skills/ghostpin-cli/`。Core 安装模块接收显式来源和安装路径，CLI 负责取得当前用户目录并传入。

先使用不跟随链接的文件类型检查区分不存在、普通目录、普通文件和符号链接，避免把断开的链接误判为首次安装。路径解析覆盖相对链接、多级链接和已有父目录中的链接。

- 安装路径不存在时，解析已有父目录并按需创建缺失目录。
- 目标是目录时，以最终真实目录为安装目标。覆盖前检查该目录中的 `ghostpin-cli` 标记是普通文件，标记链接和同名目录均不通过。
- 目标是符号链接时，保留原始链接文本及全部中间链接，只替换解析得到的真实目录。
- 断链、链接循环、非目录目标或未标记目录均报错，不自动添加标记认领目录。

考虑过删除安装路径后重新复制。该做法会删除用户建立的链接，且可能覆盖同名目录，因此不采用。

### 3. 在真实目录旁准备副本并执行替换

校验通过后，在最终真实目标的同级目录创建唯一的临时目录，完整复制并校验新 skill。临时目录与真实目标位于同一文件系统，即使逻辑安装位置通过链接指向其他磁盘，也无需跨文件系统移动。

首次安装直接提交新目录。覆盖更新先保留旧目录，再将完整新目录提交到真实目标路径。提交成功后才清理旧副本和临时项。完整目录替换会删除随包版本没有的旧文件及本地新增文件，不进行文件合并。

复制或预检失败时清理本次临时项并保留旧目录。提交失败时恢复旧目录。恢复也失败时保留旧目录副本，在错误说明中给出副本的绝对路径，禁止返回成功结果。临时项清理与安装提交必须区分，不能将已完成提交描述为原目录未变。

考虑过在旧目录上逐文件覆盖。逐文件覆盖会残留旧文件，也会在复制中途失败时产生混合版本，因此不采用。

### 4. 将安装逻辑下沉到 Core

在 `Sources/GhostPinCore/Support/` 增加独立的 skill 安装模块，使用 Foundation 完成路径、文件类型、复制和替换操作。模块接收显式路径及可注入的文件操作依赖，返回最终真实安装目录，便于构造复制、提交和恢复失败的行为检查。

`main.swift` 只增加 `init` 的参数解析、帮助优先处理、资源与用户路径获取、模块调用和结果输出，不创建 `TodoStore`。普通文本输出实际目录；`init --json` 返回 `{"ok": true, "path": "<实际安装目录>"}`。失败沿用 `CLIFailureResponse`，参数错误退出码为 2，其他失败为 1。

保持单一安装行为，不增加通用插件安装框架或额外依赖。

### 5. 使用隔离入口验证 CLI 和发布包

Core 检查使用显式临时路径，覆盖首次安装、整目录替换、旧文件清理、链接保留、归属拒绝及失败恢复，并注册到现有 `checks` 数组。

CLI 集成检查在临时目录创建 App 布局，复制 Debug CLI 和 skill 夹具。在 Debug 构建中新增仅供检查使用的 `GHOSTPIN_TEST_SKILLS_ROOT`，重定向 skill 的安装父目录；Release 不读取该变量。继续使用独立的任务隔离根，确认 `init` 不创建或修改任务数据。测试不修改 `HOME`，不对本机真实安装目录执行初始化。

发布 Workflow 保留原有签名和 DMG 检查，增加构建 App 及只读挂载 DMG 的完整目录比对，包括相对路径、文件类型、内容和归属标记。执行随包 CLI 的 `init --help` 验证帮助入口，不在本机用户目录执行 Release 初始化。

## Risks / Trade-offs

- [旧安装没有归属标记]：按用户要求拒绝自动覆盖。文档说明用户核实目录归属后迁移旧目录或补充普通文件标记，命令不自动绕过保护。
- [链接目标位于仓库或其他磁盘]：更新会作用于最终真实目录。输出实际安装路径，并在目标的同级目录准备副本与备份，保留全部原链接。
- [整目录替换移除本地文件]：README、skill 和命令帮助明确说明覆盖范围；只对带标记的目标执行替换。
- [目录提交或恢复失败]：通过可注入的文件操作构造失败检查。恢复失败时保留旧副本并报告位置，不把部分完成描述为安装成功。

## Migration Plan

1. 在源 skill 中加入归属标记及初始化说明，同时接入 CLI 和两个 App 打包入口。
2. 完成 Core、隔离 CLI、开发 App 和 DMG 检查，再按既有发布流程交付新版本。
3. 用户安装或升级 App 后显式执行 `init`。旧目录没有标记时拒绝覆盖；若安装路径链接到已补充标记的项目目录，直接在真实目录执行更新并保留链接。
4. 已提交的覆盖更新不保存长期历史版本。如需回退 skill，使用经过确认、带归属标记的旧版本内容重新安装；临时备份只服务于本次失败恢复。
